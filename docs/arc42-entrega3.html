2. Software Architecture Canvas (atualizado)

BlocoConteúdo
Business CaseReduzir o tempo entre o pedido e a entrega do prato, eliminando a comanda em papel: o cliente pede pelo celular, a cozinha recebe o ticket na hora e o gerente enxerga o gargalo em tempo real.
Business ContextRestaurantes de pequeno e médio porte (SaaS multi-tenant), mesas com QR Code, estações de produção (grill, fritura, bar, sobremesa) e equipe de salão e cozinha.
Functional OverviewCardápio digital versionado, comanda eletrônica pelo QR Code, KDS por estação com SLA e alerta, CRUD completo de comandas, fechamento, painel agregado (/aggregated-data) e auditoria.
Quality Goals1. Latência na cozinha · 2. Resiliência e degradação parcial · 3. Isolamento multi-tenant · 4. Evolutibilidade e deploy independente · 5. Observabilidade · 6. Economicidade
Organisational ConstraintsEquipe de 4 alunos · um semestre · créditos estudantis (Azure for Students e camadas gratuitas) · LGPD
Technical ConstraintsReact 18 + Vite + Module Federation · BFFs Node.js 22 (Fastify) · Microsserviços Java 21 / Spring Boot 3.5 em Vertical Slice · Spring Cloud Gateway · MongoDB Atlas (catálogo) · Azure SQL Database (pedido) · PostgreSQL no Neon (produção, estabelecimento) · LavinMQ na CloudAMQP (AMQP, compatível com RabbitMQ) · Azure Functions · Keycloak · Docker Hub · Azure Container Apps (gateway, BFFs, serviços e microfrontends) · política do Azure for Students restrita a 5 regiões
Architecture OverviewDois shells carregam remotes independentes; todo tráfego entra pelo API Gateway, que roteia para o BFF da experiência. O bff-admin agrega MS1, MS2 e a Azure Function. Cada microsserviço tem banco próprio; mudanças de estado são publicadas no broker AMQP (LavinMQ) via Transactional Outbox e consumidas de forma idempotente.
Architecture HypothesesAssíncrono entre pedido e produção absorve picos · BFF por experiência evita payloads inúteis · Vertical Slice reduz o custo de novas funcionalidades · MongoDB acomoda modificadores heterogêneos · Azure SQL garante transação conjunta agregado + outbox.
Technical Challenges & RisksConsistência eventual · operação de 9 contêineres e 4 tipos de armazenamento · versionamento de contratos · SSE com reconexão · limites das camadas gratuitas (Azure SQL serverless pausa, CloudAMQP com poucas conexões).

6.4 Decisões arquiteturais novas

ADRDecisãoMotivo e consequência
ADR-13pedido-service no Azure SQL Database, com migrações por fornecedor (db/migration/{vendor})Exigência da entrega e transação local agregado + outbox. A mesma camada JPA roda em Azure SQL e PostgreSQL; testes de contrato executam nos dois bancos (PostgreSQL embutido e SQL Server via Testcontainers).
ADR-14Azure Function status-operacional (HTTP Trigger) para enriquecimentoCálculo sem estado (faixa horária, pico, multiplicador) fora dos serviços de domínio; custo zero em repouso. A regra é pura e testada sem o SDK.
ADR-15GET /aggregated-data no bff-adminA agregação é composição de tela (papel do BFF, ADR-03). Chamadas em paralelo com circuit breaker; uma fonte fora não derruba a resposta.
ADR-16Swagger dos microsserviços publicado pelo gateway em /docs/<serviço>/**Contrato público sem expor /interno/** ao navegador; o gateway calcula X-Forwarded-Prefix (trusted proxies).
ADR-17Monorepo público com projetos independentesCada projeto (Microfrontend, BFF, MS Mongo, MS SQL, Function, gateway) fica em pasta própria com README, Dockerfile, build, testes e job de CI isolados (matriz do GitHub Actions) e imagem própria no Docker Hub, preservando o deploy independente. Um único repositório mantém contratos (AsyncAPI), docker-compose, infra e documentação versionados juntos e simplifica a avaliação. O script scripts/publicar-github.sh permite separar em um repositório por projeto, se necessário.
ADR-18CRUD completo da comanda: alterar item do carrinho e cancelar comanda (exclusão lógica)Cancelar comanda com itens já na cozinha gera ItemCancelado para cada um (mesma saga da Figura 19); recusado se algo já estiver em produção.
ADR-19API Gateway com Spring Cloud Gateway em vez do AWS API GatewayO enunciado permite outro gateway. Toda a solução roda na Azure (Container Apps); um gateway AWS exigiria uma segunda nuvem, latência entre provedores e outra conta. O Spring Cloud Gateway cobre roteamento, segurança (JWT/Keycloak, tenant sobrescrito, CORS, rate limit) e entrada única, com testes de borda e ArchUnit.
ADR-20Regiões e hospedagem impostas pela assinatura Azure for StudentsA política da assinatura só permite 5 regiões (southafricanorth, canadacentral, northcentralus, spaincentral, chilecentral). Container Apps e Azure SQL ficam em Chile Central (a mais próxima dos usuários); a Function fica em Canada Central (Chile Central não tem plano de consumo). O Static Web Apps não existe em nenhuma região permitida, então os 6 microfrontends rodam como Container Apps com nginx (workflow cd-frontend.yml). O ambiente usa o modo WorkloadProfiles: o modo Express não aplica o ingresso interno nem resolve o nome curto dos apps. Oferta gratuita do Azure SQL indisponível na região: plano Basic.
ADR-21Broker LavinMQ (CloudAMQP) e PostgreSQL no NeonO plano gratuito da CloudAMQP passou a oferecer LavinMQ, que implementa o mesmo protocolo AMQP 0-9-1: exchanges topic, DLX, filas exclusivas e publisher confirms foram validados sem mudar código. Neon (PostgreSQL 16, São Paulo) evita gastar o crédito estudantil; um usuário não superusuário por banco mantém o RLS efetivo. Mongo, Neon e LavinMQ ficam todos em São Paulo.
